# Mission Contract: Add Alembic Database Migrations
## Created: 2026-03-02

## Success Criteria (must ALL be true for MISSION_COMPLETE):
□ Alembic is installed and configured with async SQLAlchemy support
□ `alembic.ini` and `env.py` use the project's existing DATABASE_URL from config.py
□ Base.metadata has a naming convention for stable autogenerated diffs
□ Initial migration captures all 3 tables (users, sessions, agent_memories) with all columns, constraints, and indexes
□ `alembic upgrade head` works on a fresh database (creates all tables correctly)
□ `alembic revision --autogenerate` produces clean "no changes" output after initial migration
□ `init_db()` in models.py no longer calls `create_all()` — replaced by Alembic
□ Tests can still create tables (create_all kept for test fixtures only)
□ The api-server starts and runs correctly with Alembic replacing create_all

## Scope Boundaries:
- IN: Alembic setup, env.py configuration, naming conventions, initial migration, create_all replacement
- OUT: Migrating to Mapped[] annotations, adding new models, CI/CD integration, production deployment scripts

## Key Constraints:
- Must use async engine (asyncpg) — the project is fully async
- Must load DATABASE_URL from the same config.py Settings class
- Alembic directory lives inside api-server/ (co-located with the app)
- Must not break existing test infrastructure

## Key Decisions Made:
- Use Alembic async template (not sync) — matches project's async-only architecture
- Add naming convention to Base.metadata — ensures stable, predictable constraint names for autogeneration
- Replace create_all() with Alembic upgrade for production — no dual-path confusion
- Keep create_all() only in test fixtures — tests need fast schema setup without migration overhead
